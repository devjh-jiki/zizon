# design-brief 스킬 설계

작성 2026-09-02. 상태: 승인 대기.

## 1. 배경

UI 를 새로 만들 때 방향을 정하는 자리가 비어 있다. 기존 `design/anti-slop-frontend` 는
브리프를 읽고 미감을 고르는 절(§1 상황 읽기)을 갖고 있지만, 그 판단의 재료가 모델의
기억뿐이다. 실제 레퍼런스를 보지 않으므로 "미니멀하게", "프리미엄하게" 같은 형용사
수준에서 결정이 멈추고, 구현 단계에서 색과 타이포를 즉흥으로 정하게 된다.

사용자가 디자이너들이 쓰는 레퍼런스 사이트 네 곳을 지목했다. Mobbin, Awwwards,
SaaSFrame, Coolors 다. 이곳의 정보를 1차 조회해서 프로젝트별 디자인 브레인스토밍
단계를 만들자는 요청이다.

## 2. 목표 / 비목표

**목표**

- 막연한 프로젝트 설명을 열어볼 수 있는 레퍼런스 URL 과 검증된 색값으로 바꾼다
- 방향 후보를 셋 제시하고, 그 셋이 서로 실제로 다르도록 강제한다
- 고른 방향을 파일 한 장으로 굳혀서 다음 세션과 다른 에이전트가 같은 방향으로 구현한다
- 랜딩과 제품 UI 를 모두 다룬다

**비목표**

- 크롤러나 트렌드 데이터베이스를 만들지 않는다. 반복 실행할 절차 하나가 산출물이다
- 스크린샷 코퍼스를 모으지 않는다
- 팔레트 생성 엔진을 만들지 않는다. 규칙과 검증 절차만 문서로 둔다
- 구현을 하지 않는다. 방향까지만 정하고 넘긴다

## 3. 확정된 결정

| # | 결정 | 근거 |
|---|---|---|
| D1 | 기존 스킬 확장이 아니라 **새 형제 스킬**을 만든다 | `anti-slop-frontend` 가 "대시보드·데이터 테이블·다단계 제품 UI 에는 쓰지 않는다"를 명시했다. Mobbin 과 SaaSFrame 은 그 배제된 영역이 주력이라 범위가 겹치지 않는다. 확장하면 그 범위 선언이 거짓이 된다 |
| D2 | **Mobbin 을 뺀다** | HTTP 403 으로 봇 차단이다. 브라우저 자동화로 우회하는 경로는 사용자가 원치 않는다고 밝혔다. 제품 UI 레퍼런스는 SaaSFrame 으로만 다룬다 |
| D3 | 실행 시점에 조회한다 (굳힌 어휘 방식이 아니다) | 요청의 핵심이 최신 트렌드 확보다. 어휘를 문서에 굳히면 만든 날짜에 고정된다. 대신 조회가 실패해도 절차만으로 끝까지 굴러가게 설계한다 |
| D4 | 조회 결과는 **「실마리」로 표시**하고 사실로 단정하지 않는다 | WebFetch 는 페이지를 작은 모델로 요약해 돌려주므로 태그 문자열이 원문 그대로라는 보장이 없다. 15분 캐시도 있다. 확정은 사용자가 URL 을 열어 확인하는 자리에서 한다 |
| D5 | 산출물은 **프로젝트에 남기는 브리프 파일**이다 | 채팅 안에서 끝내면 세션이 끊길 때 방향도 사라진다 |
| D6 | 수확 스크립트를 만들지 않는다 | 사이트 HTML 이 바뀌면 조용히 깨진다. 브레인스토밍에 필요한 정밀도가 그만큼 높지 않다 |
| D7 | 신뢰도 라벨은 **Review** 로 등재한다 | 승격 기준(트리거 점검, 테스트 2~3개, 정성 평가)을 아직 돌리지 않았다 |

## 4. 레퍼런스 사이트 실측

2026-09-02 에 직접 조회해 확인한 것이다. 이 표가 `references/reference-sites.md` 의 근거다.

| 사이트 | 조회 | URL 문법 | 글자로 읽히는 것 | 안 읽히는 것 |
|---|---|---|---|---|
| Awwwards | 200. 로그인 불필요 | `/websites/<슬러그>/`. 태그·카테고리·기술이 모두 같은 문법. 색 필터는 `/websites/?tag=X&palette=%23HEX`. 페이지는 `?page=N` | 수상작 이름, 태그(Minimal, Animation, Typography 등), 기술 스택(React, Three.js, GSAP, Webflow 등), 카테고리 | 실제 화면. 이미지다 |
| SaaSFrame | 200. 로그인 불필요 | `/categories/<슬러그>` 41종, `/patterns/<슬러그>` 8종. `/browse` 는 404 이니 쓰지 않는다 | 카테고리 이름과 수록 개수(Account Setup 597, User Onboarding 350, Dashboard 166 등), 섹션 유형(Bento Grid, Testimonial, Footer 등), 수록 브랜드 이름 | 실제 화면. Figma 다운로드는 유료 |
| Coolors | 트렌딩 페이지는 색이 JS 로 그려져 hex 를 못 읽는다 | `coolors.co/<hex>-<hex>-<hex>-<hex>-<hex>` 가 200 으로 열린다 | 없음 | 트렌딩 팔레트 |
| Mobbin | **403** | 해당 없음 | 없음 | 전부 |

**구현 중 발견. Awwwards 는 없는 슬러그에 404 를 주지 않는다.** 200 과 함께 필터가
걸리지 않은 전체 목록을 조용히 돌려준다. `/websites/premium-saas-vibe/` 와
`/websites/zzzz-not-a-real-tag/` 가 둘 다 200 으로 수백 킬로바이트의 진짜 내용을 냈다.
404 보다 나쁘다. 실패가 실패처럼 보이지 않으므로 지어낸 태그로 존재하지 않는 트렌드를
보고하게 된다. 판별 신호는 페이지 제목뿐이다. 필터가 살아 있으면 슬러그에 맞춰 제목이
붙고(`Best Minimal Websites | Web Design Inspiration`), 되돌아갔으면 `Awwwards Nominees`
다. SaaSFrame 은 정상적으로 404 를 준다. 이 사실을 `SKILL.md` 2단계와
`references/reference-sites.md` 양쪽에 박았다.

**핵심 제약.** 이 사이트들이 나르는 정보는 대부분 이미지이고 에이전트는 페이지를
글자로만 읽는다. 그래서 이 스킬은 트렌드를 자동으로 긁어오지 않는다. 글자로 읽히는
어휘와 분류는 에이전트가 가져오고, 눈으로 봐야 하는 것은 필터가 걸린 URL 을 만들어
주고 사용자가 확인하는 왕복 한 번으로 처리한다. 이 왕복은 임시방편이 아니라 정식
단계다(5절 4단계).

**Coolors 는 조회가 아니라 생성으로 쓴다.** 트렌딩을 읽을 수 없으므로 팔레트는
에이전트가 규칙에 따라 만들고, Coolors URL 로 내보내 사용자가 손으로 돌려볼 수 있게 한다.

## 5. 절차 다섯 단계

### 1단계. 프로젝트를 읽는다

다섯 축을 뽑는다. 화면 종류, 오디언스, 바이브 단어, 조용한 제약(접근성 우선·규제
산업·아동용 등), 이미 있는 브랜드 자산. `anti-slop-frontend` §1 과 같은 축이되 제품
UI 까지 넓힌다. 출력은 한 줄 요약이다.

조용한 제약은 미감 선호를 덮어쓴다. 이 우선순위는 `anti-slop-frontend` 와 같다.

### 2단계. 검색 어휘로 번역한다

이 단계가 스킬의 심장이다. 프로젝트 설명을 세 사이트가 알아듣는 슬러그로 옮긴다.

- **미감·모션·기술** 축은 Awwwards 로 간다. `/websites/<슬러그>/`
- **화면 종류·섹션** 축은 SaaSFrame 으로 간다. `/categories/<슬러그>`, `/patterns/<슬러그>`

출력은 사용자가 바로 클릭할 수 있는 URL 대여섯 개다. 슬러그를 추측해서 만들지 않는다.
확인된 슬러그 목록은 `references/reference-sites.md` 에 두고, 목록에 없는 축이 필요하면
그 사이트의 목차 페이지를 먼저 조회해서 실제 슬러그를 확인한다.

### 3단계. 1차 조회한다

2단계에서 만든 URL 을 실제로 읽어서 셋을 가져온다. 지금 올라와 있는 이름, 반복되는
태그, 쓰이는 기술 스택이다.

**조회가 실패하면 단계를 중단하지 않는다.** 조회 없이 4단계로 가고, 그 사실을
브리프에 적는다. 조회는 재료를 늘리는 것이고 절차의 전제가 아니다.

### 4단계. 방향 후보 셋을 만든다

사람이 개입하는 유일한 자리다. 각 후보에 다섯 가지가 반드시 붙는다.

1. **이름 한 줄.** 형용사가 아니라 이름으로 부른다. "차분한 임상 데이터", "고대비 에디토리얼"
2. **근거 레퍼런스 URL 두세 개.** 열어서 확인할 수 있어야 한다
3. **팔레트.** hex 다섯 개, Coolors URL, 대비비 계산 결과
4. **타이포 조합.** 본문과 제목 두 개까지만
5. **이 후보가 틀릴 조건.** 어떤 사실이 밝혀지면 이 방향을 버려야 하는가

품질 규칙 셋이 이 단계에 걸린다(6절).

사용자가 URL 을 열어보고 하나를 고른다. 셋 다 아니라고 하면 무엇이 어긋났는지 듣고
2단계의 검색 어휘부터 다시 짠다. 후보만 바꿔서 다시 내지 않는다.

### 5단계. 브리프로 굳힌다

고른 방향을 파일 한 장으로 쓴다. 경로는 이 순서로 정한다. 프로젝트에 `docs/design/`
이 이미 있으면 거기, 없고 `docs/` 만 있으면 `docs/design/` 을 만들어 거기, `docs/`
자체가 없으면 저장소 루트의 `design-brief.md` 다. 파일 이름은 언제나
`design-brief.md` 로 고정한다. 다른 에이전트가 찾을 수 있어야 하므로 이름은 협상 대상이 아니다.

파일이 이미 있으면 덮어쓰지 않는다. 읽어서 사용자에게 보여주고 갱신할지 묻는다.

그다음 인계한다. 대상이 랜딩·마케팅이면 `anti-slop-frontend` 로, 제품 UI 면 바로 구현으로 넘긴다.

## 6. 품질 규칙

### 6.1 후보 간 거리를 강제한다

세 후보는 **색 온도, 밀도, 타이포 계열, 명도 기조** 중 최소 두 축에서 갈라야 한다.

이 규칙이 없으면 사실상 같은 것 세 개가 나오고 고르는 행위가 무의미해진다. AI 디자인
제안이 실패하는 가장 흔한 지점이라고 판단해 규칙으로 박는다.

**명도 기조 축은 구현 중 스모크 테스트에서 추가됐다.** 처음 셋으로 잡았을 때, 밝은 임상
대시보드와 어두운 모니터링 보드가 「1축밖에 안 갈렸다」로 판정됐다. 둘은 명백히 다른
방향인데 라이트와 다크의 구분이 축 목록에 없어서 규칙이 놓쳤다. 축이 셋이면 규칙이
헛돈다는 실측이다. 후보를 제시할 때 어느
축에서 갈렸는지 한 줄로 밝힌다.

### 6.2 대비비는 추측하지 않고 계산한다

본문 4.5:1, 큰 글자와 UI 요소 3:1 을 라이트와 다크 양쪽에서 확인한다.

이 단계에서 기계로 확정할 수 있는 것이 이것 하나뿐이고, 동시에 AI 가 만든 팔레트가
가장 자주 틀리는 자리다. 예뻐 보이는데 글자가 안 읽히는 조합이 검증 없이 통과한다.
계산 절차와 코드 블록은 `references/direction-and-palette.md` 에 둔다. 별도 스크립트
파일은 만들지 않는다.

기준을 못 맞추면 색을 바꾸는 것이 아니라 **명도를 조정한다.** 색상은 방향이 정한 것이고
명도는 접근성이 정하는 것이다.

### 6.3 팔레트를 색으로 역조회해서 검증한다

팔레트가 정해지면 Awwwards 의 `?tag=<미감>&palette=%23HEX` 로 그 색 계열의 실제
수상작을 다시 찾는다. 결과가 비거나 전혀 다른 분위기가 나오면 그 팔레트가 그 미감에
맞지 않는다는 신호다.

조회와 팔레트 생성을 잇는 고리가 여기서 닫힌다. Awwwards 에 색 필터가 있다는 것이
2026-09-02 조회에서 확인된 사실이고, 이 규칙은 그 발견에 기댄다.

## 7. 브리프 파일 형식

`references/brief-template.md` 가 정본이 된다. 절 구성은 이렇다.

```markdown
# <프로젝트> 디자인 브리프

<조회 날짜> 기준. 방향: <후보 이름>

## 상황 읽기
<화면 종류> / <오디언스> / <바이브> / <조용한 제약>

## 고른 방향과 이유
<왜 이 방향인가. 어떤 축에서 다른 후보와 갈렸는가>

## 토큰
| 항목 | 값 |
|---|---|
| 베이스 | #xxxxxx |
| 표면 | #xxxxxx |
| 본문 글자 | #xxxxxx (베이스 대비 x.x:1) |
| 액센트 | #xxxxxx |
| 경계 | #xxxxxx |
| 제목 서체 | <이름> |
| 본문 서체 | <이름> |
| 모션 강도 | 1~10 중 <값> |
| 밀도 | 1~10 중 <값> |

Coolors: <URL>

## 레퍼런스
- <URL> <무엇을 참고했는가>

## 버린 후보와 이유
| 후보 | 버린 이유 |
|---|---|

## 조회하지 못한 것
<조회 실패나 확인 못 한 것. 없으면 「없음」>
```

**버린 후보를 남기는 이유.** 그것이 없으면 다음 세션이 같은 방향을 다시 제안하고
사용자가 같은 이유로 다시 거절해야 한다. 볼트의 「의도적으로 지운 문서」가 같은
원리로 작동하는 것이 실측됐다.

## 8. 파일 구성

`skills/design/design-brief/` 아래.

| 파일 | 담는 것 |
|---|---|
| `SKILL.md` | 다섯 단계 절차, 발동 조건, 품질 규칙 요약 |
| `SKILL.ko.md` | 위의 한국어 번역 |
| `references/reference-sites.md` | 세 사이트의 URL 문법, 확인된 슬러그 목록, 어휘 축 대응표, 무엇이 읽히고 무엇이 안 읽히는지 |
| `references/direction-and-palette.md` | 후보 셋 만드는 규칙, 거리 강제, 팔레트 규칙, 대비 계산 절차와 코드 블록 |
| `references/brief-template.md` | 7절의 형식 |

참고 문서의 `.ko.md` 는 만든다. 상세를 원본에 맡기는 요약본이면 frontmatter 에
`translation: abridged` 를 선언한다.

**`description` 은 영어로 쓴다.** 한국어 트리거는 따옴표 안 예시로 넣는다. 초안은 이렇다.

> Turn a vague project brief into a grounded design direction before any UI code exists.
> Reads the project, translates it into real filter URLs on Awwwards (aesthetic, motion,
> tech, color) and SaaSFrame (screen type, section pattern), fetches what is currently
> there, then proposes three deliberately-distinct directions, each with real reference
> links, a WCAG-checked palette plus a Coolors URL, and a type pairing. Ends by writing a
> design brief file that implementation reads. Covers both marketing surfaces and product
> UI (dashboards, onboarding, settings). Use when starting a new UI, redesigning, picking
> colors or type, or when the user says "디자인 브레인스토밍", "레퍼런스 찾아줘",
> "색 조합 뽑아줘", "트렌드 보고 정하자", "design direction", "moodboard",
> "pick a palette". NOT for reviewing existing UI code, and NOT a replacement for
> anti-slop-frontend, which implements the direction this skill picks.

## 9. 저장소 연동

스킬이 22개에서 23개가 된다. 같이 고쳐야 하는 곳이 넷이다.

1. **`.claude-plugin/plugin.json`** 의 `skills` 배열에 `./skills/design/design-brief` 를 더한다. `pnpm validate` 가 디스크와 이 배열을 대조하므로 빠뜨리면 빌드가 실패한다
2. **루트 `README.md`(한국어)와 `README.en.md`(영어)** 에 등재한다. 라벨은 Review
3. **`skills/README.md` 와 `skills/README.ko.md`** 에 등재한다
4. **`CLAUDE.md`** 의 버킷 설명에서 `design/` 항목과 스킬 개수(22 → 23)를 고친다. `plugin.json` 의 `description` 에도 개수가 박혀 있다

`anti-slop-frontend` 에는 **한 줄만** 더한다. §1 상황 읽기에 "브리프 파일이 이미 있으면
그것을 읽고 이 절을 건너뛴다"는 조항이다. 두 스킬이 같은 판단을 두 번 하지 않게 하는
것이 목적이고, 기존 범위 선언은 손대지 않는다. `SKILL.md` 와 `SKILL.ko.md` 를 같은
의미로 함께 고친다.

버전은 올리지 않는다. 이 저장소는 버전을 관리하지 않고 재설치로 반영한다.
개발 중 반영은 `./bootstrap/bootstrap.sh --dev` 다.

## 10. 검증 기준

**저장소 게이트.** 커밋 전에 셋을 돌리고 통과를 확인한다.

```sh
pnpm validate
pnpm test
python3 .github/scripts/check_doc_pairs.py
```

`check_doc_pairs.py` 는 `SKILL.md` 의 description 이 영어인지, 짝 없는 `.ko.md` 가
있는지, 번역의 제목 구조가 원본과 같은지를 본다.

**기능 확인.** 스킬을 실제로 한 번 돌려서 아래를 확인한다.

1. 2단계가 만든 URL 이 실제로 필터를 거는가. **Awwwards 는 상태 코드로 판별할 수 없다.**
   200 이 필터 성공을 뜻하지 않으므로 페이지 제목이 슬러그에 맞게 바뀌었는지로 본다
2. 4단계의 세 후보가 6.1 의 두 축 기준을 실제로 만족하는가
3. 대비비 계산 결과가 손계산과 일치하는가
4. 5단계가 브리프 파일을 실제로 쓰는가. 「버린 후보」 절이 비어 있지 않은가
5. 조회를 일부러 막았을 때 단계가 끝까지 굴러가는가. **SaaSFrame 의 없는 슬러그를 쓴다.**
   그쪽은 실제로 404 를 준다. Awwwards 로는 실패를 만들 수 없다

**5번을 반드시 돌린다.** D3 이 "조회가 실패해도 절차만으로 굴러간다"를 전제로 하는데,
그것이 실제로 성립하는지 확인하지 않으면 전제가 아니라 희망이다.

## 11. 리스크와 미결

| 항목 | 성격 |
|---|---|
| 사이트가 URL 문법을 바꾸면 2단계가 깨진다 | 감수한다. 슬러그 목록이 참고 문서 한 곳에 모여 있으니 고칠 자리가 하나다 |
| WebFetch 요약이 태그를 변형할 수 있다 | D4 로 완화했다. 단정하지 않고 실마리로만 쓴다 |
| SaaSFrame 무료 열람 범위가 바뀔 수 있다 | 조회 실패 경로(3단계)가 이것을 흡수한다 |
| Awwwards 색 필터의 매칭 정밀도를 모른다 | 6.3 이 이것에 기댄다. 첫 실행에서 실제 결과를 보고 규칙의 강도를 조정한다 |
| Mobbin 을 나중에 넣고 싶어질 수 있다 | `references/reference-sites.md` 에 403 사실과 브라우저 자동화 경로를 왜 택하지 않았는지 남긴다. 다시 판단할 때 재료가 된다 |
| 서체 이름을 제안하지만 실제 사용 가능 여부는 확인하지 않는다 | 4단계에서 서체를 낼 때 Google Fonts 수록 여부만 확인하고, 유료 서체는 유료임을 밝힌다 |
