# js-testing

JS/TS 코드베이스에서 테스트를 작성하기 *전에* 하는 판단 — 무엇을 어느 층위에서 테스트할지, 이름을 어떻게 지을지, 데이터를 어떻게 준비할지, 무엇을 검증하지 말아야 할지. 테스트를 실행하거나 구현 코드를 짜는 것과는 다른 단계다.

**역할 경계 — 세 스킬, 세 시점:**

- **`js-testing`** (이 스킬) — 아직 테스트가 없는 시점의 판단: 어느 층위, 어떤 이름, 어떤 데이터, 무엇을 검증하지 말아야 하는가.
- **`webapp-testing`** — 실제로 떠 있는 앱을 Playwright 로 구동한다 (클릭 흐름, 스크린샷, 콘솔·네트워크 로그). 브라우저 레벨 실행이 필요하다고 판단된 다음에 쓴다.
- **`superpowers:test-driven-development`** — 구현하면서 도는 red-green-refactor 루프. 어떤 테스트를 써야 할지 결정하고 실제로 작성하려는 시점에 쓴다.

"이걸 유닛 테스트로 할지 통합 테스트로 할지"는 여기. "Playwright 로 이 버튼을 어떻게 클릭하지"는 `webapp-testing`. "이 함수를 구현하는데 첫 테스트를 뭘 써야 하지"는 TDD.

## 증류이지 전량 이식이 아니다

원문: [goldbergyoni/javascript-testing-best-practices](https://github.com/goldbergyoni/javascript-testing-best-practices) (MIT), 테스트 구조·백엔드·프론트엔드·커버리지·CI 전반에 걸친 50개 이상의 항목. 그중 대부분은 이미 합의된 상식이거나 도구별 세부사항이다 (AAA 구조, E2E 에서 `sleep()` 쓰지 않기, 오류를 catch 하지 말고 expect 하기, 실제와 비슷한 가짜 데이터 쓰기, 속도별로 테스트 태깅하기) — 실력 있는 개발자라면 여기서 망설이지 않으므로, 여기 다시 옮기면 판단 가치 없이 컨텍스트만 소모한다. 아래는 정답이 상황에 따라 갈려서 합리적인 개발자들도 서로 다른 결론에 도달하는 항목만 남긴 것이다. 나머지는 원문을 읽어라.

## 1. 테스트 층위 선택

**원칙:** 고정된 피라미드 비율이 아니라, 실제 위험이 있는 곳에 테스트 층위를 맞춘다.

**왜 갈리는가:** 테스트 피라미드는 로직이 많고 유닛을 분리하는 비용이 싼 코드를 전제로 한다. 통합 중심 서비스(비즈니스 로직은 얇고 대부분 DB·큐·API 를 엮는 일)는, 정작 중요한 걸 다 mock 으로 걷어낸 유닛 테스트 열 개보다 그 배선을 포함하는 컴포넌트·통합 테스트 하나가 테스트-분당 실질 커버리지가 더 높다. 어디부터가 "얇다"인지는 규칙이 아니라 판단이다.

**판단 기준:** "이 함수의 내부 구현이 다른(하지만 결과는 동일한) 구현으로 바뀌어도 이 테스트가 수정될 필요가 없는가?"를 물어라. 코드 대부분이 분기 로직 없는 배선이라면, 그 배선을 포함하는 층위(컴포넌트·통합)에서 테스트한다. 분기·엣지 케이스·계산처럼 진짜 판단 로직이 있는 조각이 있다면, 그 조각만 유닛 테스트로 분리하고 주변 배선은 상위 층위 테스트에 맡긴다.

## 2. 테스트 이름 3부분 구조

**원칙:** 테스트 이름 한 번 읽는 것만으로 세 가지 질문에 답해야 한다 — 무엇을 테스트하는지, 어떤 상황인지, 무엇을 기대하는지. 그래야 코드를 열지 않고도 테스트 리포트만으로 실패 원인을 진단할 수 있다.

**왜 갈리는가:** 사소한 테스트에서는 이게 장황하게 느껴지고, 이름에 "should" 를 명시적으로 넣어야 하는지도 팀마다 갈린다. 아이디어 자체에 대한 이견이 아니라, 장황함의 비용이 어디서부터 이득을 넘어서는지에 대한 이견이다.

**판단 기준:** 코드를 모르는 사람 — 미래의 나 자신, CI 실패를 보는 동료 — 이 테스트 이름만 보고 뭐가 깨졌는지 알아야 한다면 세 부분을 다 쓴다 (`describe(단위) > describe(상황) > it(기대결과)`). 작성자 본인만 읽는 파일 안의 소수 테스트라면, 이 구조를 다 갖추는 게 얻는 게 없다.

## 3. 블랙박스 원칙

**원칙:** 공개 동작과 결과만 검증한다. 내부 구현이 리팩터링·이름 변경되어도 관찰 가능한 결과가 맞다면 테스트는 절대 깨지지 않아야 한다.

**왜 갈리는가:** 내부 헬퍼를 직접 유닛 테스트하고 싶은 유혹은 항상 있다 — 이미 분리돼 있고, mock 도 덜 필요하고, assertion 도 더 단순해진다. 그런데 그 유혹이 가장 강한 지점이 바로 곧 리팩터링될 가능성이 가장 높은 코드다.

**판단 기준:** 그 내부 요소가 자기만의 계약을 갖는가 — 그 함수를 호출하는 곳과 별개로 소비·배포·추론되는 대상(공유 유틸리티, 모듈 경계)인가? 그렇다면 사실상 public 이니 직접 테스트한다. 반대로 언제든 인라인될 수 있는 순수한 구현 디테일이라면, 직접 검증하지 말고 public 진입점을 통해서만 간접적으로 거친다.

## 4. 테스트 데이터 — 공유 픽스처 대신 팩토리

**원칙:** 각 테스트가 필요한 데이터를 스스로 만들고 소유한다(테스트 안에서 호출하는 팩토리 함수·빌더). 전체 스위트를 위해 한 번 시딩해 둔 데이터에 기대지 않는다.

**왜 갈리는가:** 공유·시딩된 픽스처는 실제로 설정이 빠르고, 읽기 전용(순수 조회) 테스트라면 시딩된 데이터를 재사용하는 것도 정당하고 의도적인 성능 트레이드오프다. 이견은 "더 빠름"이 커플링 비용을 넘어서는 지점이 어디인지에 있다.

**판단 기준:** 그 테스트가 자신이 읽는 데이터를 변경하는가(다른 테스트도 건드리는 레코드를 update·delete·insert)? 그렇다면 항상 팩토리로 만든 자기 데이터를 쓴다 — 변경 + 공유 상태는 정확히 "원인이 엉뚱한 다른 테스트"인 실패를 만든다. 읽기만 하고 절대 변경하지 않는 테스트라면 시딩된 공유 데이터도 받아들일 만한 선택이다 — 다만 기본값이 아니라 의도적으로 선택해야 한다.

## 5. 스냅샷의 함정

**원칙:** 스냅샷은 짧고 인라인일 때만 쓴다(리뷰어가 업데이트를 승인하기 전에 실제로 읽을 수 있는 몇 줄) — 아무도 들여다보지 않는 큰 외부 파일로는 쓰지 않는다.

**왜 갈리는가:** 크게 자동 생성된 스냅샷은 공짜 커버리지처럼 보이고, 실제로 일부 회귀는 잡아낸다. 문제는 "diff 가 바뀌었으니 accept" 가 뭔가를 검증하는 행위인지, 아니면 그냥 눈으로 훑고 도장 찍는 리뷰 피로 연극인지다.

**판단 기준:** 그 스냅샷이 바뀐 PR 에서, 리뷰어가 승인 전에 diff 를 실제로 읽을까, 아니면 JSON·DOM 덩어리를 대충 훑고 넘어갈까? 실제로 읽는다면 스냅샷이 제 역할을 하는 것이니 그 정도 짧기를 유지한다. 승인이 반사적이라면, 문서 전체 대신 실제로 중요한 특정 필드·형태(또는 스키마 검증)에 대한 assertion 으로 바꾼다.

## 6. 커버리지의 함정

**원칙:** 커버리지 퍼센트는 테스트 실행 중 어떤 줄을 *지나갔는지*를 재는 것이지, 어떤 동작이 *검증됐는지*를 재는 게 아니다 — assertion 이 하나도 의미 있는 걸 확인하지 않아도 100% 가 나올 수 있다.

**왜 갈리는가:** 커버리지 게이트를 강제할 가치가 있는지 팀마다 갈린다. 회의론자들 말대로 숫자 하나로는 아무것도 증명되지 않지만, 게이트 옹호자들 말대로 임계값이라도 있으면 테스트 하나 없는 PR 이 머지되는 건 최소한 막는다. 둘 다 서로 다른 실패 모드에 대해 맞는 말을 하고 있다.

**판단 기준:** 커버리지는 바닥선(테스트가 아예 닿지 않은 코드를 잡아내는 용도)으로만 쓰고, 천장 목표나 품질의 대리지표로 쓰지 않는다. 테스트가 줄을 지나가는 것 이상으로 뭔가를 검증하는지 확인하려면, 눈으로 직접 물어본다: "이 비교 연산자나 반환값을 뒤집으면, 실제로 실패하는 테스트가 있는가?" — 이 질문을 자동화한 것이 뮤테이션(mutation) 테스트다. 도구 없이도 이 판단은 직접 적용할 수 있다.
