# Go 백엔드 리뷰

기계가 판단할 수 없는 수준에서 Go 백엔드 diff를 리뷰한다: 경계의 의도, 데이터 무결성, 실패 모드 규율, 관용적 설계. 모든 지적에는 독자가 검증할 수 있는 근거(프로젝트 정본 조항 또는 공개 Go 규범)를 붙인다. 취향만으로 지적하지 않는다.

## 2층 모델

1. **기계 게이트가 먼저다.** gofmt, golangci-lint, 아키텍처 린터(예: go-arch-lint), API Breaking 검사는 CI의 몫이다. 도구가 잡을 위반이 diff에 있으면 한 줄로 언급하고 넘어간다. 나열하지 않는다.
2. **이 스킬은 판단이 필요한 것만 본다**: 아래 4개 렌즈.

## 렌즈 1: 아키텍처와 경계

- 도메인 계층이 프레임워크·HTTP·DB 드라이버를 import하는가 (금지)
- 한 모듈이 다른 모듈의 테이블을 애플리케이션 포트 없이 직접 쓰는가
- 핸들러에 유스케이스 호출과 오류 매핑 외의 로직이 있는가
- 도메인 엔티티를 DTO 없이 API 응답으로 직접 직렬화하는가
- "나중의 분리를 위해" 투기적 추상화나 조기 네트워크 간접화를 넣었는가 (YAGNI)

## 렌즈 2: 데이터 무결성과 결정성

- 계산 함수가 현재 시각·외부 API를 입력으로 받지 않고 내부에서 읽는가 (결정성: 같은 입력 스냅샷 + 같은 규칙 버전 = 같은 결과)
- 금액이 최소 단위 정수인가, 비율이 basis point 또는 명시적 decimal인가 (float 금지)
- 재현성이 요구되는 곳에서 규칙 버전·입력 스냅샷·계산기 버전이 결과와 함께 저장되는가
- 백그라운드 잡 핸들러가 멱등적인가, 잡 페이로드에 개인정보 원문이 들어가는가 (금지)

## 렌즈 3: 오류·보안·개인정보

- 오류 응답이 프로젝트 오류 모델(예: RFC 9457 Problem Details)을 따르며 내부 메시지·SQL·개인정보를 누출하지 않는가
- 로그가 프로젝트의 상관관계 키(trace/request/job ID, 해시된 사용자 ID)로 구조화되어 있는가
- 외부 fetch가 등록된 도메인 allowlist를 강제하는가 (SSRF)
- 인증 토큰 클레임(iss, aud, exp, kid)을 헤더 신뢰가 아니라 실제로 검증하는가

## 렌즈 4: Go 관용구

Google Go Style Guide, Go Code Review Comments, Uber Go Style Guide 기반:

- 에러 래핑(`%w`)과 컨텍스트 전달, `panic`은 복구 불가능한 시작 실패에만
- 인터페이스는 사용 측에서 작게 정의, 공급 측 거대 인터페이스 금지
- goroutine 수명과 채널 소유권 명시, 누수 금지
- 테이블 주도 테스트, 프로젝트가 정한 곳에서는 실제 의존성 통합 테스트(예: testcontainers)
- `SELECT *` 금지, 쿼리 생성기 사용 시 쿼리 이름·cardinality 명시

## 출력 형식

심각도순 정렬: `파일:라인 / P0 (정확성 파괴·데이터 누출) | P1 (정본 위반) | P2 (권고) / 문제 / 근거 (정본 조항 또는 규범) / 제안`. 확신 없는 지적은 질문형으로. 마지막에 프로젝트 완료 기준(DoD) 중 diff가 해당하는 항목만 체크한다.

## 프로젝트 어댑터 계약

이 스킬은 **코어**다. 각 프로젝트는 어댑터(예: 프로젝트 스코프 에이전트 파일)로 다음을 주입해야 한다:

1. 백엔드 변경의 완료 기준(DoD) 체크리스트
2. 정본 도메인 enum, 버전 표기 형식, 금지 패턴
3. 리뷰 산출물 저장 위치와 커밋 가능 여부

어댑터 컨텍스트가 없으면 리뷰 상단에 "범용 렌즈만 적용, 프로젝트 정본 미주입"을 명시하고 렌즈 1~4로 진행한다. 참조 구현: jjan 모노레포의 `be-reviewer` 에이전트 (문서 저장소의 결정 기록(DDR)과 백엔드 완료 기준을 주입).

## 하지 않는 것

- 스타일·포맷 지적
- 기계 게이트가 잡을 위반의 재나열
- diff 밖 코드의 전면 재설계 요구
- 인용 가능한 근거 없는 취향 지적
