# 프론트엔드 리뷰

프론트엔드 diff 를 스타일 체크리스트나 특정 리뷰어 인물 재현 대신, 6개의 명시적 렌즈로 리뷰한다. 모든 지적은 diff 안에서 독자가 검증할 수 있는 것을 가리켜야 한다 — 빠진 케이스, 불일치, 문서화되지 않은 규칙. 취향만으로는 지적하지 않는다.

## 입력

기본 리뷰 대상은 `git diff main...HEAD` 다. 호출자는 대신 다음을 지정할 수 있다:

- 파일 목록
- 커밋 범위 (`git diff A..B`)
- PR (해당 PR 의 diff 를 가져온다)

이 중 어느 것도 비어 있지 않은 diff 로 이어지지 않으면, 그 사실을 말하고 멈춘다 — 전체 트리를 대신 리뷰하지 않는다.

## 6개 렌즈를 순서대로 적용

각 렌즈마다: 질문을 던지고, 체크리스트를 diff 에 대조하며, 체크리스트 중 실제로 걸리는 게 있을 때만 지적한다. 아무것도 걸리지 않는 렌즈는 늘어난 트집이 아니라 한 줄 "해당 없음"으로 통과시킨다.

1. **요구사항 추적성** — 이 코드가 무슨 요구사항을 만족시키는지 읽히나
2. **추상화 비용** — 이 추상화가 벌어들이는 것보다 비싸지 않나
3. **상태의 위치** — 전역·컨텍스트로 올라간 상태가 정말 그 자리여야 하나
4. **인터페이스 예측가능성** — 이름과 시그니처가 실제 동작과 일치하나
5. **비동기 UX** — 로딩·에러·빈 상태가 설계되었나
6. **숨은 동작** — 호출자가 모르는 부수효과가 있나

각 렌즈의 전체 내용 — 질문, 3~5개 체크리스트, 실제 코드에서 가져온 before/after 예시 하나 — 는 [references/lenses.ko.md](references/lenses.ko.md) 에 있다.

## 출력

항상 두 가지를 낸다:

1. **인라인 지적** — 응답에 바로 드러낸다. 항목마다 어느 렌즈인지 밝힌다.
2. **작성된 보고서** — `<repo>/docs/reviews/YYYY-MM-DD-<주제>.md` 에 저장한다. 상단 헤더 블록:

```markdown
# <주제>

- 일시: YYYY-MM-DD
- 대상 범위: <git diff main...HEAD | 파일 목록 | 커밋 범위 | PR 번호>
- 리뷰어: fe-review
```

그 아래에 렌즈별로 묶은 지적을 적고, 각각에 이유와 (도움이 되면) 제안하는 수정을 붙인다. 특정 렌즈에서 diff 가 걸리지 않으면 그 렌즈는 생략한다 — "문제 없음"으로 채워 넣지 않는다.

## 하지 않는 것

- **스타일·포매팅 지적 안 함** — 들여쓰기, 세미콜론, import 순서, 줄바꿈 같은 것은 린터·포매터의 몫이다. 그 도구가 잡을 것을 이 리뷰가 다시 나열하지 않는다.
- **취향 차이를 결함으로 포장하지 않음** — "나라면 이렇게 안 짰다"는 근거가 아니다. 지적하려면 여섯 렌즈 중 하나에 걸리는 구체적 이유를 댄다.
- **근거 없는 추측 안 함** — diff 에 없는 코드의 동작을 추정해 지적하지 않는다. 확신이 없으면 질문형으로 쓰거나, 확인이 필요하다고 명시한다.
